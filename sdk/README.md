# perseverus-sdk

The wallet SDK for BTC Medusa. It lets a wallet buy token packs and then find out how exposed a transaction's inputs are before it broadcasts, without telling the server which inputs it is asking about. It's written in Rust on top of `core`, `circuits` and `client-native`, with Kotlin and Swift bindings generated by [UniFFI](https://mozilla.github.io/uniffi-rs/), the same approach the BDK and LDK bindings use.

## API

| Kotlin | What it does |
|---|---|
| `Perseverus.connect(Config)` | Sets up the transport, opens local storage and reads `GET /v1/meta` (API version, OPRF key, current epoch month). Refuses a server whose API major version differs or that needs a newer SDK. Optionally pins the OPRF key. Set `provingKeyPath` to the `pk.bin` bundled with your app; the production server doesn't serve it. |
| `buyTokens(method, plan)` → `Purchase` | Starts a Lightning (trial or onetime) or card (onetime, monthly or yearly) purchase via `POST /v1/tokens/purchase`. Show the user `paymentRequest`. The server sets the price. Test servers may also sell Lightning `DEV` (100 tokens for a few cents) for integration testing. |
| `addPurchase(id, plan)` | Records a purchase made outside the SDK (e.g. a card checkout finished in a browser) so it can be redeemed. |
| `purchaseStatus(id)` → `PENDING`/`PAID`/`REDEEMED`/`EXPIRED` | Polls `GET /v1/tokens/purchase/{id}/status`. |
| `redeem(id)` → `List<PackInfo>` | Blinds tokens, gets them signed via `POST /v1/tokens/redeem` and unblinds them. One pack for most plans; a yearly card plan returns 13 (this month plus the next 12). The claim goes out on its own Tor circuit. |
| `tokenBalance()` / `listPacks()` | Computed on the device; the server never learns balances. They fetch the current month (`GET /v1/meta`) to decide which packs are active. |
| `importPack(blob, method)` | Adds a pack blob in Sparrow's format, e.g. migrated from Sparrow or restored from a backup. |
| `analyzeInputs(inputs, AnalyzeOptions)` → `AnalysisResult` | The pre-broadcast call. Returns one `PrivacyReport` per input. |

`PrivacyReport` follows `docs/blueberry-v1/privacy-report.schema.json`. Each report has a `status`:
- `GRADED`: the funding transaction was found and decoded.
- `UNGRADED`: the transaction is excluded by the skip rules. This is not a privacy flag.
- `NOT_COVERED`: there is no filter yet for that block.
- `ERROR`: the analysis failed for that input.

All finding text comes from `docs/blueberry-v1/findings-catalog.v3lean.json`. That file is compiled into the SDK, so Sparrow and the SDK show the same wording.

Every call **blocks**, so run them off the main thread.

Errors from the server arrive as `PerseverusException` with `reason` set to `"<code>: <message>"`, where `<code>` is the stable `/v1` error code (`nullifier_spent`, `payment_required`, `upstream_unavailable`, …; see `docs/blueberry-v1/openapi.yaml`). Match on the code, not the message.

The SDK talks only to the `/v1` API.

## How `analyzeInputs` protects the user

1. Inputs are grouped by funding transaction, because v5 filters are keyed per transaction.
2. The SDK downloads filters for the real block heights mixed with Laplace decoys and shuffled, at most 200 heights per request.
3. Matching happens on the device. If a txid isn't in its block's filter, the input is `UNGRADED`; if the block has no filter, it's `NOT_COVERED`. **Neither costs a token.**
4. The SDK reserves **one token per matched funding transaction**, saves the reservation, then sends all the Groth16 spend proofs in one OPRF request over a fresh Tor circuit. That request carries no heights or txids.
5. It checks the server's DLEQ proof, decrypts the codebook code, looks up the 24-bit tag and builds the report.

## Design choices

- **Tor fails closed.** `Transport.Tor` never falls back to clearnet. There's no OHTTP option because `client-native`'s OHTTP mode is still a stub that connects directly. `Direct` is for development only, and `connect` refuses to use it with a `.onion` endpoint.
- **Tokens are marked used before the spend request goes out.** If the server rejects an individual spend before burning it, the token is given back. If the whole request fails in transit, the token stays marked used, because the SDK can't tell whether the server burned it.
- **Packs are stored in Sparrow's blob format.** That format was moved out of the Sparrow-only JNI module into `client-native/src/pack_blob.rs`, and the Sparrow build is unchanged.

## Build and test

```bash
cargo test  -p perseverus-sdk                                    # Java parity (500 tags) + schema
cargo test  -p perseverus-sdk --release --test e2e -- --ignored  # full pipeline vs in-process server
cargo build -p perseverus-sdk --release --lib
cargo run   -p perseverus-sdk --features bindgen --bin uniffi-bindgen -- \
  generate --library target/release/libperseverus_sdk.so --language kotlin --out-dir sdk/bindings/kotlin
```

The generated bindings (`com.btcmedusa.perseverus`, about 3k lines) are gitignored and should be built in CI. On Mac the library file is `.dylib`.
